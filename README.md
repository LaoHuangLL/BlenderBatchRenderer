这是基于 [YueMoon99/BlenderBatchRenderer] 的个人修改版，仅用于个人备份学习。

1. 修复了“预计剩余时间（ETA）”计算错误的 Bug
2. 修复了进程残留导致的“拒绝访问”问题
3. 新增“并行任务数”功能
4. 系统监控新增“显存占用（VRAM）”显示
5. 优化了参数提取的容错与超时机制
6. 新增“打开工程”按钮

## 2026/10/24（本次更新）

这一轮专门处理“关闭程序时卡死 / 拒绝访问 / 系统卡顿只能重启”。

**根因结论**：卡死不是程序没退出，而是 Windows 把进程置成了「终止中」状态——某个线程正跑在内核态
（显卡驱动里），杀了也杀不掉，此后再强杀只会返回 `Access is denied`，只能重启。
现场证据：卡住时进程只剩下 **1 个线程**，模块表里加载着 `nvml.dll`（显卡监控库）；同时 NVIDIA 内核驱动
（`nvlddmkm`）在两次卡死的同一时刻都在报 `Graphics FECS Exception` / `Error occurred on GPUID: 100`。
也就是说**显卡驱动在那一刻出故障，把程序带进了内核态**，程序是受害者。

因此本次改动分两方面：一是不再让程序主动去碰显卡驱动，二是把退出流程做得更彻底、更容易查。

- **显卡监控默认关闭**（配置项 `"gpu_monitor": false`）。关闭时后台不加载 `nvml.dll`、不向驱动发任何查询。
  需要显示 GPU/显存数字时，在 `BlenderBatchRenderer_config.json` 里把 `gpu_monitor` 改成 `true` 即可。
- **去掉每秒一次的 `nvmlInit()` / `nvmlShutdown()`**：旧代码每轮询一次就把 NVML 初始化再关闭，
  导致 `nvml.dll` 被反复加载/卸载，而且 `nvmlShutdown()` 会打断别的线程正在进行的查询。
  现在改为进程内单例，只初始化一次、不再关闭。
- 显卡查询只在后台线程执行，GUI 线程只读缓存；某次查询超过 2 秒还没返回就**永久停用显卡监控**，
  绝不把界面和“关闭”一起拖进驱动里。
- 修正 `TerminateProcess` 的 Win32 签名：旧写法没声明 `argtypes/restype`，64 位句柄被按 32 位截断，
  所以**从未真正强杀过自己**，每次都静默退化成 `os._exit()`（也就是逐 DLL 卸载通知那条容易死锁的路）。
  现在能真正终止，并且会把返回值和错误码写进日志（错误码 5 = 已在「终止中」，外部强杀也一样）。
- 管道读取改为 `PeekNamedPipe` 轮询：去掉了会在退出时死等 `stdout.read(1)` 的读线程，
  也不再跨线程关闭正在被读取的句柄（这在同步管道上是取消不掉的）。
- 删除无用的 `CTRL_BREAK` / `FreeConsole` “优雅停止”：Blender 后台模式不处理 SIGBREAK，纯副作用。
- 结束子进程改为**批量处理**：一次 `psutil` 拿到整棵进程树、共用一个截止时间，不再逐个 `taskkill` 干等，
  并行 8 个任务时也不会把界面僵住十几秒。“停止渲染”按钮同样改成批量 + 总截止时间。
- 退出流程全部带时限：后台清理 2.5s，总硬上限 9s，到点由看门狗强制结束本进程；
  最后一步「结束自己」回到 GUI 主线程执行（从其他线程调 `ExitProcess` 会抢加载器锁）。
- 退出日志改写到三处（当前目录 + 程序目录 + `%TEMP%`），并新增启动记录与显卡监控状态记录，
  下次卡住直接能看出卡在哪一步、有没有碰驱动。
- 退出期间不再弹出「关机/重启」确认框（`_exiting` 守卫）。
- 新增诊断脚本 `diagnose_hang.ps1`，见下。

## 2026/09/27

- 手动中断后再次开始渲染，"总渲染进度"不再归零：Blender 会自动跳过的已渲染帧同样计入进度。
- 停止渲染/关闭程序时会彻底清理本程序启动的所有 Blender 子进程，不会再残留关不掉的僵尸进程。
- 关闭程序不再卡在后台或出现"拒绝访问"：退出前取消并关闭子进程管道 IO，并直接结束自身进程，不再等待卡住的线程。
- 退出时不会连带杀掉用【打开工程】手动打开的 Blender。
- 上一次渲染失败过的任务，重新渲染成功后不再被误标为"渲染出错"。
- 帧步长等参数填 0 时，进度统计不再抛除零错误。
- "总渲染进度"保留一位小数（帧数上万时不会再长时间显示 0%）。
- 进度按帧号去重统计：Blender 重渲已存在的帧不会重复计数，进度只增不减、也不会超过 100%。
- 开始渲染前自动扫描输出目录，兼容"输出路径是目录"和"文件名前缀"两种写法，目录下带前缀的命名（如 镜头_0001.png）同样能识别。
- 渲染过程中每 15 秒自动回扫一次输出目录，漏算的帧会自动补进进度，无需重新开始渲染。
- 扫描不到已渲染帧时，日志会给出示例文件名，便于定位"输出路径 / 命名不匹配"的问题。
- 总帧数、进度、ETA 统计口径统一，"自动填入缺失帧"场景下的进度同样准确。
- 已渲染帧号写入会话文件，重开软件续渲进度不丢失；旧版本存档自动兼容，进度不会倒退。
- 退出时会话/配置改为同步写入并原子替换，避免强退或断电导致存档损坏。
- 退出时关闭单实例服务，避免下次启动连接到已失效的管道。
- 修复渲染完后不会自动停止的问题。

## 诊断工具：diagnose_hang.ps1

**什么时候用**：程序卡住关不掉（窗口无响应 / 任务管理器里还能看到进程 / 系统整体变卡）时，
**别急着强杀，先跑它**，然后再重启。

```
powershell -NoProfile -ExecutionPolicy Bypass -File .\diagnose_hang.ps1
```

也可以指定进程名（不要带 `.exe`）：

```
powershell -NoProfile -ExecutionPolicy Bypass -File .\diagnose_hang.ps1 -Name BlenderBatchRenderer_Pro
```

它会打印并保存（脚本旁边的 `diagnosis_result.txt`，不会往当前目录乱写）：

- 进程的线程数、句柄数、内存、是否响应；
- **「终止中」状态判定**：线程数 ≤ 2 且仍有线程不在等待状态时，直接报 `TERMINATING-STATE SIGNATURE`
  ——这种情况任何用户态手段都杀不掉，只能重启；
- 进程里加载了哪些显卡驱动模块（`nvml` / `nvcuda` / `nvapi` / `opengl32` / `d3d11` / `d3d12` / `dxgi` / `amdadl` ...）；
- 线程按 `State/WaitReason` 的分布（全 `Wait/UserRequest` 说明进程自身健康）；
- 残留的 `blender.exe`、退出日志尾部、显卡型号与驱动版本；
- 近 7 天的 `Display 4101`（TDR：显示驱动停止响应并已恢复）、应用无响应、以及 `nvlddmkm`
  内核驱动事件统计（含 `FECS Exception` / `GPUID` 明细）。

判读规则：`threads` 只剩 1~2 个、并且事件日志同时有 `nvlddmkm` 报错 → 是显卡驱动/硬件的问题，
不是本程序的 bug。这时该做的是：用 DDU 彻底卸载并重装显卡驱动、把显卡超频/降压恢复默认、
临时禁用模拟器的虚拟显示器驱动（如 `MuMu Virtual Display Adapter`）。
